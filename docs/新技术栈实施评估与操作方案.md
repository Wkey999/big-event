# BOOM 新技术栈实施评估与操作方案

> 2026-10-29 基于本地后端 `D:\workplace\big-event`、前端 `D:\workplace\VUE_CODE\big-event-web`、`D:\workplace\AI文档助手-项目灵感与交接.md` 及 [20 号 RAG 交接](备忘录/20-文档助手RAG升级与前端体验优化交接.md) 核对。本文是供 Gemini 审阅的实施决策，不表示这些功能已部署。两个仓库目前均有未提交改动；实施时应逐项复核 Git 状态，不覆盖其他工作。

## 一、结论与范围

BOOM 的核心仍是 **Vue 3 + Spring Boot 3 + MySQL 的内容社区**。新技术应回答实际问题：Redis 解决 JWT 显式退出；Python/FastAPI 承担文档处理；RAG 解决私有资料的有据问答；Docker Compose 改善可复现部署。MCP、A2A、OCR、LangGraph 和全站 TypeScript 改造可以作为后续实验，不能为了简历关键词同时铺开。

推荐顺序：**收束当前未提交改动与真实联调 → Redis → 现有最小 RAG 的真实调用与引用质量验收 → 持久化和语义检索实验 → Docker Compose → 按需要选择 OCR/MCP/A2A**。README、架构图、演示脚本和测量表与每阶段同步更新，不等所有功能做完再补。

## 二、动手前的统一基线

1. 在两个仓库分别运行 `git status --short`、检查当前分支和差异；记录已修改文件及归属。仅对本阶段文件动手，绝不把其他工作顺手提交。先备份业务库，再执行增量迁移；测试写入只在明确隔离的测试库。
2. 保留既有本地接口契约：前端 Axios `/api` 代理剥前缀，Java 原生接口如 `/document/analyze`。Vue Router 使用 History 模式；上线时 Nginx 需继续回退到 `index.html`。
3. 先跑后端 Maven 测试、前端构建、Python 单测及本地登录链路，记录通过/失败/未验证。当前代码中的 Python `/health` 与 Java `/document/analyze` 单测不等于完整登录后端到端验收。
4. 所有模型与存储密钥留在服务端私有配置，测试资料使用自行编写、可公开的文档。生产实例的 IP、指纹、余额和资源占用会变化，上线前重新检查；本方案不授权直接部署、购买或开放新端口。

## 三、Redis：先完成一个能解释的使用场景

**实施对象**：已有 `TokenRevocationService`、JWT 拦截器、`POST /user/logout`、`docs/Redis会话退出.md`。当前 `AUTH_TOKEN_REVOCATION_ENABLED=false` 时不依赖 Redis。

1. 本机启动 Redis，只监听回环地址 `127.0.0.1:6379`；确认服务存活和密码配置。不要把 6379 放到公网。需要跨 Redis 重启保留已撤销令牌时启用 AOF，并验证恢复行为。
2. 在本地私有环境把 `AUTH_TOKEN_REVOCATION_ENABLED=true`，重启 Java；注册/登录，保存测试 JWT，退出后用**同一个旧 JWT**请求受保护接口，应得到 401；新登录的 JWT 应正常。测试 Redis 停止时是否按当前设计返回 503，不允许已退出令牌“复活”。测试令牌不写入文档和日志。
3. 为真实 Redis 增加隔离的集成测试或手工验收记录；已有模拟测试只能证明代码分支。确认内存、AOF 磁盘和故障处理后，才评估云端启用。
4. 回滚只需在服务端私有配置关闭功能并重启 Java；回滚会恢复旧的无撤销语义，须在发布记录中写明。不要宣称该方案已实现单设备登录或所有设备强退。

## 四、Python 文档助手：从原型到最小 RAG

**现有本地代码**：`document-assistant/app/main.py` 的 `POST /v1/analyze` 接收最多 20,000 字符文本和问题，提供 BM25、TF-IDF、Hybrid RRF 与 Overlap 检索；`POST /v1/extract` 支持 TXT/MD/可提取文字的 PDF。Java `DocumentAssistantController` 通过登录网关调用回环地址 Python 服务，并在平台/自有 API 模式中可选地生成回答；Vue `/documents` 页面已有对应入口。生产默认关闭，文档不持久化，真实模型回答质量与线上链路尚未验收。

### 第 1 步：收束现有链路

本地启动 Python `python -m uvicorn app.main:app --host 127.0.0.1 --port 8001`，再启动 Java 和 Vue。登录后分别测试摘录、平台生成和自有 API 生成，以及有答案、无答案、空文本、超长文本、Python 停止、超时。平台/自有 API 真实调用前先确认配置与费用；摘录模式明确标记为零模型调用。

### 第 2 步：最小文件问答

现有上传入口已支持 TXT、MD 与可提取文字的 PDF，并对可能的扫描件给出错误提示。下一步先验收真实文件边界，再做持久化：Java 保存 `document(id, owner_id, filename, status, size, content_hash, created_at, ...)` 等元数据；原件存储方式沿用现有 OSS 经验，但使用私有对象/授权读取，避免把私人文档放在公开图片 Bucket。Python 负责提取、分块和检索；每个片段保留文档 ID、片段 ID、文件名及可靠时的页码。上传、查询、删除都按服务端取得的 `owner_id` 限定，不能信任浏览器传入的用户 ID。还需校验文件真实类型，而不只根据后缀判断。

现有问答代码已向 Python 取相关片段、无片段时拒答、复用现有模型路由与平台配额，并过滤模型输出中不属于候选集合的引用编号。继续验收“有片段但答非所问”“引用合法编号却不支持该断言”“生成模式无问题时做摘要”“配额不足/上游失败”等情况。**编号过滤只是格式/来源合法性校验，不是语义事实核验，也不能保证消除幻觉。**保留免费额度/用户自填 API 的边界，检查真实调用和失败计次语义，不得绕过预算。

文档持久化阶段再新增“上传/状态/提问/删除”接口，而不是继续扩张一次性传全文的 `/document/analyze`。原接口暂时保留给演示页面，迁移后再决定是否弃用。每次调用记录检索耗时、生成耗时、是否有证据、费用估算与错误类别；日志不打印文档全文、片段正文或 API Key。

### 第 3 步：向量检索对比

现有 28 题自编问答可作为回归基线，但语料仅 18 个片段且四种方法的有答案 Hit@1 均为 100%，不足以证明策略优劣。先补充更长的留出文档、难例和人工标注，再在 Python 侧评估 CPU FastEmbed + 支持中文的 embedding 模型（候选 `BAAI/bge-small-zh-v1.5`）及 Qdrant 本地模式。官方文档列出该模型并说明 FastEmbed 可在 Python 进程本地生成向量；具体模型版本、下载体积和 2 核 4 GiB 服务器实测仍须确认。[Qdrant FastEmbed 模型清单](https://qdrant.tech/documentation/embeddings/fastembed/)、[本地向量生成示例](https://qdrant.tech/documentation/tutorials-basics/generate-embeddings-fastembed/)

保持关键词与向量两种检索模式可切换，比较 Recall@K、无答案误召回、引用正确率、P50/P95 响应时间和内存；不得只挑演示成功的问题。向量数据写入时带文档 ID、所有者与模型版本；查询时做服务端归属过滤。换 embedding 模型或分块规则时建立新索引并回填，验证成功后切换，避免新旧维度混查。只有指标与资源可接受才把向量模式设为默认。即使增加向量库，生成模型仍需要独立调用与费用控制。

## 五、Docker Compose：先用于可复现的测试环境

以当前真实线上结构为基准，先做多阶段 `Dockerfile`（Java 构建/运行）和 Python 镜像，再用 Compose 定义 Nginx、Java、Python、MySQL；Redis 仅在已通过联调后加入。前端构建产物交给 Nginx。数据库和检索索引用命名卷，密钥通过未入库的环境文件/密钥挂载提供，容器内只开放必要内部端口；公网只开放 80/443，3306/6379/8001/9090 不暴露。Compose 健康检查需覆盖 MySQL、Java、Python；设置资源限制、重启策略和日志轮转。

先在**独立本地/测试环境**验证：空库迁移、登录、上传、问答、重启后数据读回、备份与恢复、前端深层链接刷新、服务故障及回滚。不要在现有生产机上直接执行会重建数据库容器的 `compose up`。如果容器化没有改善复现与发布，保留现有 systemd 部署完全合理。Docker 官方也建议生产环境使用单独的 Compose 覆盖配置，并按服务重建/部署。[Docker Compose 生产说明](https://docs.docker.com/compose/how-tos/production/)

## 六、CI、可观测性与论文证据

GitHub Actions 首批只做后端编译测试、前端构建、Python 单测、敏感文件/配置示例检查；不自动部署。把部署改为明确的人工触发并绑定受保护环境之前，先做好回滚和备份。服务健康检查区分“进程活着”与“依赖可用”，日志保留请求关联 ID、错误分类和耗时，但不记录私人资料。README 放一张实际架构图、一段本地启动、一组可重复演示步骤，并逐项标注代码完成、本地验证、线上验证状态。

毕业设计实验建议至少保留两条可对照基线：**现有 MySQL 文章关键词检索**与**文档助手关键词片段检索**；如果做向量模式，再作为第三条实验路径。不要把不同任务的分数混成一个指标。记录数据集来源、测试问题、人工标注的相关片段、检索命中、答案有据率、无答案拒答率、延迟和模型费用。对外只展示有授权或自编资料；导师提出的公开数据集要求另行对齐，不能用私人文档实验直接替代。

## 七、MCP、A2A、OCR：触发条件与最小实验

- **MCP**：现有 `@Tool` 只在 Spring AI 应用内调用，不是 MCP。若将来希望 Gemini/Codex 等不同客户端复用 BOOM 的“查询公开文章”“查询公开榜单”能力，可单独做只读 MCP 服务。先限定公开或最小授权数据，工具参数与返回都加长度/权限限制，禁止暴露用户私文档、管理写接口和任意 SQL。只有跨客户端互操作真实跑通才写进简历。MCP 标准区分 tools、resources、prompts；本项目适合从只读 tool 开始。[MCP 官方说明](https://modelcontextprotocol.io/specification/)
- **A2A**：当“资讯研究 Agent”需要委托“文档分析 Agent”完成独立任务、双方具有独立身份/能力说明/任务状态时，再考虑 A2A。现在 Java 同步调用 Python HTTP 服务只是普通微服务通信；包装成两个 Agent 会增加认证、状态、超时、幂等和日志复杂度。先做独立本地样例，不接生产写操作。A2A 官方定位是独立 Agent 之间互通。[A2A 官方概览](https://a2a-protocol.org/)
- **OCR**：只对扫描件或图片文字识别有真实需求时加入。先在本地比较 10 份自编样本的识别率、耗时、内存与误字对问答的影响；OCR 结果须允许用户核对，错误文本不能伪装成原文证据。
- **LangGraph / 多轮记忆**：只有出现明确的多步骤状态和中断恢复需求再引入。当前单次问答由普通服务调用即可完成。
