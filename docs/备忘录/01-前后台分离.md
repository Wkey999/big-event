# 备忘录 01：前台与后台分离（得物式消费端 vs 管理端）

## 一句话目标

前台 = **消费**（推荐流、搜索、频道、作者主页，参考得物）；后台 = **管理**（内容、频道、作者、审核、任务监控）。
两者在**入口、布局、接口、权限**四层分开，管理员不再"混在信息流里"。

## 现状（代码事实）

1. **后端没有 `/admin` 命名空间**：现有路由只有 `/user/**`、`/article/**`、`/category/**`、`/profile/**`、`/dev/**`。
   管理能力（改删任意文章、建改删频道）与消费接口**混在同一组路径**里。
2. **管理员纵览是"隐式分叉"实现的**：
   `service/impl/ArticleServiceImpl.java:205` → `Long queryUserId = isAdmin() ? null : userId;`
   同一个 `GET /article/list`：普通用户看自己（含草稿），管理员看全站（含他人草稿）。
   由此 `state`、`mode=recommend`、`total` 对两种角色**语义并不一致**。
3. 详情/编辑/删除同样在 Service 内现场分支：`isAdmin()` 出现在 `ArticleServiceImpl` 的 L80 / L123 / L145 / L154。
4. `user` 表只有 `role`（0 普通 / 1 管理员）与 `status`，**没有"后台账号"这一独立概念**。
5. 前端 `views/HomeView.vue`（消费端）与 `views/article/ArticleManageView.vue`（管理）虽已分文件，但**共用同一套接口与登录态**，没有角色落地页与独立布局。

## 问题

- **同接口两套语义**：前端必须"先知道我是谁"才能正确使用 `/article/list`；管理员在前台点"我的文章"看到的其实是全站，容易误操作。
- **权限散落**：判断写在 Service 内部，新增接口时容易漏；没有统一入口就没有统一护栏。
- **交互目标冲突**：消费端要"顺滑、沉浸、无按钮负担"；管理端要"批量、可筛选、有状态"。混在一起两边都别扭。

## 方案（三步走，可独立交付）

### 第一步：后端加 `/admin/**`（低风险，前端暂不动）

- 新增 `AdminInterceptor`（校验 `user.role = 1`）并注册到 `/admin/**`；`ThreadLocalUtils` 复用现有用户上下文。
- 迁移管理员专属能力到 `/admin`，示例契约：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/article/list` | 全站文章，支持 `state`、`authorId`、`categoryId`、`keyword`、`pageNum/pageSize` |
| GET | `/admin/article/{id}` | 含正文与作者信息 |
| PUT | `/admin/article/{id}` | 编辑任意文章（不改作者） |
| DELETE | `/admin/article/{id}` | 软删任意文章 |
| PUT | `/admin/article/{id}/state` | 上下架（草稿↔已发布） |
| POST/PUT/DELETE | `/admin/category/**` | 频道管理（从 `/category` 迁入） |
| GET | `/admin/user/list` | 用户/作者管理（含 AI 作者，见备忘录 03） |

- **前台 `/article/list` 回归单一语义**：只返回**已发布的共享内容**，不再按角色分叉；管理员要看全站请走 `/admin/article/list`。

### 第二步：前端路由与布局分离

- `/`：消费端（瀑布流 + 推荐/最新 + 频道 + 搜索入口），参考得物首页结构。
- `/admin`：独立布局（侧边菜单 + 顶部面包屑 + 表格/表单），菜单项：文章、频道、作者(AI)、审核队列、任务监控、数据看板。
- 登录后按 `role` 落地：`role=1` → `/admin`（但**允许**从前台"以用户视角预览"）。
- 前台卡片上可为 `role=1` 显示一个"管理"小入口（编辑/下架），兼顾便利性。

### 第三步：契约与字段分离

- 后台接口**可以**返回 `content`、作者、审计字段；前台接口**永不返回 `content`**（沿用现有"列表收窄列"约定）。
- 后台列表支持批量操作（批量下架/删除/指派频道）。

## 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 破坏性变更 | `HomeView` / `ArticleManageView` 现在依赖 `/article/list` 的管理员语义 | 先加 `/admin/**` 并行，前端切完后再收紧前台语义（同版本发布或分两次发） |
| 管理员便利性下降 | 不能再在信息流里直接删文 | 前台保留 role=1 可见的"管理"小入口 |
| 权限回归 | 迁移过程中可能出现"旧接口仍可越权" | 迁移后对旧接口补测试：普通用户访问 `/admin/**` 必须 403；管理员访问前台接口结果与普通用户**完全一致** |

## 验收标准

1. 普通用户通过**任何**接口都无法看到他人草稿（列表/详情/编辑/删除逐个验）。
2. 管理员全部管理能力集中在 `/admin/**`；未登录/普通用户访问 `/admin/**` 返回明确拒绝（401/403，且不泄漏资源是否存在）。
3. 前台接口对管理员与普通用户返回**完全一致**的已发布数据（同一 `pageNum/pageSize/mode` 结果一致）。
4. 前端存在两个独立布局，登录后按角色落地正确。
