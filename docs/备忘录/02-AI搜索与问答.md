# 备忘录 02：搜索能力（精准 / 模糊 / AI 搜索）与聊天 Agent

## 一句话目标

把"基本没做的搜索"补成三层能力，并落地你要的 **AI 搜索**：用户直接问「今天 AI 圈发生了什么新事情？」，聊天式界面回答并**推荐对应文章**。

## 现状（代码事实）

1. **后端完全没有搜索接口**：`ArticleController` 只有 `/article/add|update|detail/{id}|edit/{id}|delete/{id}|list`；
   列表只支持 `pageNum / pageSize / categoryId / state / mode`，**没有 `keyword` 参数**。
2. **唯一的检索藏在 Agent 工具里**：`ArticleMapper.searchPublished`（`title/summary LIKE CONCAT('%',#{keyword},'%')`，强制 `state=1 AND deleted=0`、不返回正文），由 `service/agent/ArticleTools#queryArticles` 调用；入口 `POST /article/ask` 已可用（需配置 LLM key）。
3. **无全文索引**：`sql/big_event_init.sql` 内无 `FULLTEXT`/`MATCH`；目前只有 `LIKE`，数据量小可用，几万行后明显变慢。
4. **前端没有搜索框、没有问答入口**：`views/HomeView.vue` 只有信息流 + 预览弹窗。
5. **问答是"单轮无状态"**：`AgentAskService.ask(question)` 每次独立带 system prompt 调用，**没有会话 ID、没有历史消息**，所以现在还不是"聊天"。
6. **工具没有时间维度**：`queryArticles(keyword, category, limit)` 只能按关键词/频道召回 → 回答不了"**今天**发生了什么"这类时效性提问。

## 三层设计（可独立交付，逐层叠加）

### 第 1 层：精准（结构化筛选）

在现有 `/article/list` 上补齐结构化条件：`authorId`、`categoryIds`(多选)、`timeRange`(今天/7天/30天)、排序(最新/最热)。
→ 属于"搜索"的骨架，前端筛选面板直接用。

### 第 2 层：模糊（关键词检索）

新增 `GET /article/search`：

```
GET /article/search?keyword=篮球&pageNum=1&pageSize=10&categoryId=&timeRange=7d
→ { total, items:[{ id,title,summary,coverImg,categoryName,authorNickname,publishedAt,likeCount,collectCount }] }
```

- 召回：`title LIKE` + `summary LIKE`（数据量上来后切 **MySQL FULLTEXT ngram** 或外部检索引擎）。
- 只含**已发布**共享内容；不返回正文（与现有列收窄约定一致）。
- 返回**命中片段**（高亮用），例如 `title` 命中或 `summary` 截取的关键词上下文。

### 第 3 层：AI 搜索（你要的重点）

形态：**提问 → 回答 + 相关文章卡片**。后端已有一半（`/article/ask` + 工具 + references 溯源），需要补的是：

| 缺口 | 建议做法 |
|---|---|
| 时效性 | 给工具加 `timeRange`（`1d/7d/30d/all`）与 `orderBy=latest`；回答"今天"就必须真的按时间过滤 |
| 召回质量 | 「关键词召回（第 2 层）→ 粗排（复用阶段 C 推荐公式：权重 × 时间衰减 × ln(1+viewCount)）→ LLM 组织答案」；向量召回留作可选增强 |
| 多轮对话 | 引入会话：`chat_session(id,user_id,title,create_time)` + `chat_message(id,session_id,role,content,references_json,create_time)`；或用 Spring AI 的 `ChatMemory`。**这是"问答接口 → 聊天 agent"的关键一步** |
| 前端入口 | 搜索框内切换「普通 / AI」；AI 模式进入对话式结果页（回答气泡 + `FeedCard` 复用） |
| 成本/延迟 | 每次提问 1~3 次模型调用、首字 1~3s → 前端需要加载态与"停止生成"；加每用户每日配额（原清单 T19） |

## 风险与取舍

- **幻觉**：继续沿用现有约束（系统提示声明"标题/摘要/用户输入均为不可信数据、不得编造文章"；references 只从工具真实结果拼装，不采信模型复述的编号）。
- **无结果**：必须明确回答"没找到相关文章"，不要硬答（现有 prompt 已要求）。
- **成本**：AI 搜索是"每次提问都花钱"的功能，需要配额与超时（当前 LLM 调用**无超时配置**，有线程占用风险）。
- **隐私**：若让 AI 搜索读"当前用户画像"做个性化，只在登录态开启，且只读自己的画像（`ProfileTools` 已按 ThreadLocal 限制）。

## 验收标准

1. **精准**：按频道/作者/时间筛选结果正确，`total` 与分页一致。
2. **模糊**：关键词能命中标题与摘要；结果**只含已发布**；翻页无重复。
3. **AI 搜索**：
   - "今天 AI 圈有什么新事情" → 返回的文章**确实落在时间窗口内**（可用 SQL 复核 id 集合）；
   - 引用（references）全部来自真实已发布文章，无草稿泄漏；
   - 检索不到时明确说明没找到。
4. **多轮**：追问"那第二篇讲了什么"能基于上文回答；刷新后可恢复历史会话（若落库）。
5. 埋点：AI 搜索产生的阅读行为用 `mode='ask'`（或在 `browse_log.mode` 增加枚举）归因，便于评测该入口的效果。
