## 1. 目标与范围

让社区持续获得有来源、可追溯的 AI／科技内容：机器人定时发现更新，第一版整理标题、作者、时间和原文链接，写入网站数据库，经过审核后进入信息流和搜索。后续如需增加摘要、正文或 AI 整理，先核对来源的具体授权；AI 检索仅使用实际保存且获准使用的信息。

首批接入下表两个来源，现已扩展到六个（见第 10 节），共用一套采集程序和审核流程，每个来源对应一个禁止登录的机器作者。不扩展成多套 Agent 服务，不同时引入多个工作流平台。

固定数据集用于可重复的检索与推荐评测；实时采集用于社区内容更新。两类数据记录来源，评测时冻结数据版本，避免内容每天变化导致结果不可比较。

## 2. RSS 是什么，内容从哪里来

### 本次讨论确定的首批来源

| 来源 | 订阅地址 | 采用范围 |
| --- | --- | --- |
| 阮一峰的网络日志 | https://www.ruanyifeng.com/blog/atom.xml | 科技周刊、工具与项目发现；保留作者和原文入口 |
| GitHub 官方博客 | https://github.blog/feed/ | 筛选 AI 技术、开发实践、开源相关内容；不整站导入促销、套餐或活动营销 |

用户接受广泛的 AI 相关内容，不限定为资讯、工具或论文中的某一种。用户已将美团技术团队移出接入名单，原因是其企业专属内容与社区定位不匹配。GitHub 博客也包含自身产品宣传，因此必须按内容筛选，不能将“官方博客”直接等同于中立资讯。

这两个订阅源已完成技术读取验证；这不等同于取得转载、改写或配图授权。初版仅做文章标题、作者、时间和原文链接卡片，不复制全文与图片，不自动改写发布。阮一峰周刊页面的许可包含署名、非商业性使用和禁止演绎条件；需要转载或改写时另行核对具体许可范围。以上是本次实现的边界。

RSS／Atom 是网站发布更新清单的格式，不是新闻供应商。实际内容来自科技媒体、技术团队博客、个人博客等具体发布者。订阅条目通常包含标题、原文链接、时间，部分含摘要或全文；不能假定每个源都提供完整正文。

来源优先顺序：网站官方 API → 网站自行提供的 RSS／Atom → 经逐个验证的其他来源。

RSSHub 部分路由底层仍涉及网页抓取；转换成 RSS 不会改变其采集方式。当前先选择主动提供接口或订阅的来源，不安排自写通用爬虫。

## 5. 最小处理流程

```text
定时读取两个官方订阅源
  → 解析并校验条目
  → 按主题和原文发布时间筛选
  → 按规范化原文 URL 的 SHA-256 唯一索引去重
  → 整理标题、作者、时间、来源链接
  → 先存入独立待审表，尚不生成社区文章
  → 管理员审核发布
  → 进入社区信息流、搜索与问答检索
```

新内容先自动入库为待审记录，未通过审核时不写入 article。稳定后可增加“指定来源允许自动发布”的配置，默认关闭。本版仅调用模型翻译 GitHub 标题，不生成摘要或正文；AI 问答不能凭标题补写原文观点。

建议以独立来源记录关联现有 article，本版保存来源名称、规范化原文 URL、原文发布时间、采集时间、机器人作者和关联文章。原文时间未知时留空，不能把采集时间伪装成事件发生时间。去重约束由数据库保障，重复执行和失败重试不应产生重复文章。

外部接口调用和模型整理放在数据库写事务之外，写入文章与来源关联采用短事务。重复条目逐条跳过；来源读取或数据库失败记录本次失败和已插入数量，下次采集会按唯一索引继续。没有额外的重试队列或重试次数字段，日志不保存密钥。

## 6. 在 Web 网站里的呈现

- 首页：与普通文章共用卡片，显示机器作者标识、来源名称，避免冒充原作者原创。
- 详情页：展示原文标题、来源、作者、原文发布时间、收录时间和原文入口；不展示导读、正文或配图。
- 后台：先提供手动采集、采集记录、待审草稿和审核发布入口，后续再增加来源配置界面。
- 检索：仅已发布内容进入公开检索。只保存链接或摘要的内容，AI 不应声称读过来源全文。

Agent 可后续承担主题判断、栏目选择、导读与摘要整理。固定调度、去重、失败重试和数据库写入由普通工程代码负责。

## 7. 使用方式与实际验收

### 启动与操作

1. 已有数据库执行 `sql/migration/006_content_feeds.sql`；新库也须在基础建库与既有迁移后执行此脚本。脚本只新增三张表，适配 MySQL 5.7，不修改历史文章。
2. 启动后端与前端，以管理员登录，访问 `/admin/feeds`（管理后台 → 资讯采集）。
3. 两个来源都可「立即采集」，新条目进入「待审核」。选择「审核发布」及频道后才进入社区；「忽略」会保留去重记录，后续不会再次导入。
4. 「已发布」可查看卡片；已发布内容的下架或删除仍走原有内容管理。机器作者是链接整理者，原作者在来源区单独署名。

`application.yml` 中的配置：

| 配置项（app.content-feeds 下） | 默认值 | 含义 |
| --- | --- | --- |
| enabled | true | 自动采集开关，关闭后仍可管理员手动采集 |
| initial-delay-ms | 60000 | 启动后 60 秒首次执行 |
| interval-ms | 1800000 | 一轮执行结束后间隔 30 分钟 |
| max-new-per-source | 5 | 每来源单次最多新增 5 条 |
| max-new-per-day | 60 | 全来源每日最多新增 60 条，待审也计入 |
| max-new-per-source-per-day | 10 | 每来源每日最多新增 10 条，避免单个快讯源占满额度 |
| max-age-days | 30 | 过滤原文发布时间超过 30 天的条目 |

可用环境变量 `APP_CONTENT_FEEDS_ENABLED=false` 关闭自动任务。服务需要保持运行，尚未部署为常驻线上服务。首次发布时惰性创建 `rss_ruanyifeng`、`rss_github`，普通权限、禁止登录，无需人工设置密码。

固定来源白名单；仅请求订阅地址，不抓取文章页面。请求连接超时 5 秒、请求超时 15 秒、等待上限 20 秒，响应体最多 2 MiB，单源最多检查 200 个条目，拒绝 HTTP 重定向和 XML DOCTYPE。已知原文 HTTP 链接升级为 HTTPS，移除跟踪参数和片段后去重。当前采集互斥与每日配额适用于单实例；多实例部署前需要分布式调度或数据库配额锁。

GitHub 按标题与栏目标签做规则筛选，并排除部分促销／活动词；规则不能保证全部相关或完全排除营销，因此保留人工审核。原文发布时间缺失时留空，不回填采集时间。

## 9. GitHub 中文标题（2026-10-19 增补）

- 新增迁移 `sql/migration/007_feed_title_translation.sql`，在执行 006 后运行；MySQL 5.7 上可重复执行，英文原题不覆盖。
- GitHub 采集结束后，取最多 10 条尚无译名的待审记录，批量调用项目已有 ChatClient 翻译标题。只发送条目 ID 与公开英文标题，不发送正文、登录凭据或其他用户信息；翻译调用不具备检索工具或发布权限。
- 英文原题保存在 `feed_entry.title`，中文译名保存在 `translated_title`。模型结果按 ID 对应，校验数量、ID 唯一性、中文字、长度、标签与控制字符；无效响应不会冒充翻译成功。翻译失败不丢失原文条目，可以「补译待审标题」或在审核框中手动填写。
- 补译接口为管理员 `POST /admin/feeds/github/translate`；只处理 GitHub、待审、尚无译名的条目。已翻译或已发布条目不会重复调用或覆盖；本版为单实例互斥，不支持多实例去重调用。
- 审核列表中文为主、英文为辅。审核时可以修改中文标题，随后选择频道并发布；GitHub 缺少有效中文标题时拒绝发布。人工修改和发布在同一事务完成。取消审核不会修改库中译名。
- 发布快照保留 `source_title` 英文原题和 `source_translated_title` 中文译名；首页、阅读页、搜索结果和问答引用优先显示中文，检索支持中文译名与英文原题。旧的已发布链接保持原状，未经再次审核不自动变更其公开标题。
- 本机真实模型调用批量补译 8 条，全部仍是待审，未代用户发布。重复补译返回 0 条；浏览器验证双语列表、审核框编辑与取消。后端测试由 63 项增加到 72 项，前端构建通过。

翻译依赖已有 `app.llm.enabled=true` 与本地模型配置，会产生模型请求和用量；未启用或服务异常时可手动填写。订阅读取仍只访问 RSS／Atom，不因标题翻译而抓取文章正文。前端采集与补译请求等待上限为 90 秒，长时间网络失败后仍可刷新检查已入库状态。
