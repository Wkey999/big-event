# 备忘录 05：工作流程与排期（含 GPT 评审采纳）

> 本文是四份备忘录的**执行编排层**：范围控制、阶段任务、协作流程、验收口径。
> 采纳了 GPT 评审意见（01 → 02 → 03/04 顺序、/admin 并行先行、SQL 级时间过滤、`browse_log.mode` 补 `ask`）。

## 0. 已确认决策（截至 2026-10-11）

| 决策 | 结论 |
|---|---|
| 图片 | **D 变体：预置场景图池 + 按频道/主题匹配**（先人工建几张相关性图，AI 选题时调用场景图） |
| 服务器 | **先不租**，正式上线再租（本地闭环 → 上线前上轻量） |
| 采集范围 | 只做摘要 + 必须附原文链接（不全文搬运） |
| 范围控制 | **01 前后台分离 → 02 搜索 → 03/04 内容自动化与资讯源（后置扩展）** |
| AI 作者权限 | 单独加 `user_type`，**不得复用 `role=1`** |
| 检索基线 | 先 `LIKE`（title/summary），不急着上向量库 |
| 时效性 | 「今天发生了什么」必须 **SQL 真实限定时间范围**，不能只靠提示词 |
| 埋点归因 | `browse_log.mode` 增加 `ask` 枚举（与 AI 搜索埋点同步） |

## 1. 范围控制（毕设核心 vs 扩展）

**核心闭环（必须完成，答辩主线）**：
01 前后台分离 + 02 普通搜索 + 02 AI 搜索（**单轮**）+ 问答入口 UI + 时间过滤 + 埋点 `mode=ask`。

**扩展（有设计、可后置/选做）**：
多轮会话、向量检索、03 AI 作者、04 资讯源采集、审核队列增强、服务器部署、RSSHub 扩源。

> 理由：核心闭环本身已能串成「社区结构清晰 + 智能搜索可演示」的完整故事；扩展项做进设计文档即可体现前瞻性，答辩可讲"为什么后置"。

## 2. 里程碑顺序（依赖关系）

```
M0 准备(图池+协作规范) → M1 前后台分离 → M2 搜索闭环(普通 + AI 单轮) → M3 内容自动化(扩展) → M4 上线(服务器)
```

- M1 是 M2/M3 的"容器"（后台要放审核队列、源管理）。
- M2 拆两步：**2a 普通搜索**（独立可交付）→ **2b AI 搜索增强**（在 `/article/ask` 上增强）。
- M3 依赖 M1 的 `/admin/**`；M4 只在"正式上线"前启动。

## 3. 分阶段工作流

### 阶段 0：准备（半天）

- [ ] 人工建 4~5 张场景图（AI热点 / 篮球 / 足球 / 电竞 / 通用）→ 上传 OSS
- [ ] 登记图池映射（先硬编码 `category_id → image_key`，后建 `scenario_image` 表）
- [ ] 把「写手=OpenCode / 验证+提交=DSH」协作规范写进 `AGENTS.md`（建议）
- 验收：图池 URL 可访问；AGENTS.md 存在

### 阶段 1：前后台分离（01，后端并行接口先行）

**目标**：不破坏现有信息流，加 `/admin/**` 并行，前端切完再收紧前台语义。

- [ ] 后端：`AdminInterceptor`（校验 `user.role=1`）+ 注册到 `/admin/**`
- [ ] `AdminArticleController`：`/admin/article/list`（全站，state/authorId/categoryId/keyword/分页）、`/admin/article/{id}`（含正文）、`PUT`/`DELETE`、`PUT /{id}/state`（上下架）
- [ ] `AdminCategoryController`：频道增改删（复用 Service，加角色护栏）
- [ ] **权限回归测试**：未登录 401；普通用户 403；管理员可用；对不存在 id 返回与「无权限」一致的模糊错误（延续现有防探测口径）
- [ ] 前端：`/admin` 独立布局 + 侧边菜单 + 登录按 `role` 落地；卡片上 `role=1` 显示「管理」入口
- [ ] **里程碑 M1**：收紧 `/article/list` 为「仅已发布、所有用户一致」——删除 `ArticleServiceImpl:205` 的 `isAdmin() ? null : userId` 分叉，**前后端同步发版**

**验证侧（DSH）检查点**：普通用户对所有旧接口的越权测试；管理员走前台接口的结果与普通用户**完全一致**；`mvn test` + 真实启动 + 冒烟。
**风险**：收紧前台语义是破坏性变更，必须同版本前后端一起改（`HomeView` 不再依赖管理员语义）。

### 阶段 2：搜索（02）

**2a 普通搜索（独立可交付）**
- [ ] 后端 `GET /article/search?keyword&categoryId&authorId&timeRange&pageNum&pageSize`（LIKE title/summary，仅已发布，不返回正文，返回命中片段）
- [ ] 前端搜索框（普通）+ 结果页（复用 `FeedCard`）

**2b AI 搜索增强**
- [ ] `ArticleTools.queryArticles` 增加 `timeRange`(1d/7d/30d/all) + `orderBy`；**SQL 层面限定时间**（传参拼条件，不许只靠 prompt）
- [ ] `browse_log.mode` 增加 `ask`：`BrowseLogDTO` 的 `@Pattern(regexp="latest|recommend|ask")` + 前端 `reportBrowse` 归因
- [ ] 前端问答入口 UI（搜索框 AI Tab → 回答 + 推荐卡片）
- [ ] 多轮会话 —— **标记为扩展**，核心阶段只做单轮

**验收（M2）**：「今天 AI 圈有什么新事」→ 返回文章**确实落在 24h 内**（SQL 复核 id 集合）；references 真实、无草稿；检索不到明确说没找到；埋点 `mode=ask` 生效。
**验证侧**：真实 LLM 冒烟（同 t17 套路）+ DB 复核时间过滤正确性。

### 阶段 3：内容自动化（03/04，扩展）

- [ ] 表结构：`user.user_type` + `login_enabled`；`content_source`；`fetch_log`；`article.source_*`；`scenario_image`
- [ ] 单源闭环：官方 API（优先 HN/arXiv/GitHub）→ 去重 → LLM 摘要（仅陈述源文事实）→ 场景图选图 → 草稿 → **人工审核** → 发布
- [ ] kill switch（`app.bot.enabled=false`）+ `/admin` 审核队列
- [ ] 扩源：RSSHub（先公共实例验证路由，再本地 Docker）
- 验收：周期内新增去重草稿；摘要 + 原文链接必填；审核闸门生效；kill switch 立即停止

### 阶段 4：上线准备（正式上线前再启动）

- [ ] 轻量服务器（届时再租：国内 2C2G 起学生机，或香港/新加坡免备案）
- [ ] Docker Compose（app + MySQL + RSSHub + Nginx）；配置外置已就绪
- [ ] 备案（若绑域名，提前 1~2 周）、安全组、`mysqldump` 备份
- 验证侧：重启自愈、备份可恢复、密钥不落盘（沿用外置方案）

## 4. 协作流程（写手 / 验证者）

- **写手**：OpenCode —— 每次只做**一个阶段内**的原子任务；提交前自测 `mvn test` + 真实启动一次。
- **验证 + 提交**：DSH —— 流程：冻结确认 → 代码审查 → `mvn test` → 真实启动/冒烟 → 密钥扫描 → 规范提交 → 代理推送 → 远程核对。
- **交接口令**：写手完成说「交接完毕」；DSH 检测到并发写手 → 立即停手警告。

## 5. 不做清单（范围护栏）

1. 暂不做向量检索（先 LIKE 基线）
2. 暂不做多轮会话（核心只做单轮）
3. 不全文搬运、不代理盗图（图片走 D 图池）
4. AI 作者不授 `role=1`
5. 服务器现在不租
6. 不引入 Spring Security（等真需要细粒度权限/审计再评估；现阶段手写拦截器够用）
